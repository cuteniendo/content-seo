Internal reference · content operations

Blog Content Pipeline

repo: cuteniendo/content-seo

Six Claude Skills that take a client from a live URL to QA‑checked, Word‑ready blog drafts. No slash commands to memorize — you trigger it by describing what you want in plain language, the same way you'd ask a colleague.

01

The six stations

Each phase is its own skill and can run standalone — useful for re‑doing just one step, like re‑running QA after a hand edit.

1 · Intake

Client Intake

Opens the client's Cowork project in Chrome, reads Instructions, Memory and knowledge files.

"find the project context for Island Route"
2 · Research

Keyword Research

Pulls ranking and opportunity keywords for the domain via DataForSEO.

"keyword research for australiancreditsavers.com.au"
3 · Cluster

Keyword Clustering

Groups the keyword list into one topic per planned post — reports a shortfall rather than padding it.

"cluster these keywords"
4 · Draft

Content Generation

Writes one full post per cluster, in the client's own brand voice and word‑count rules.

"write the blog posts for these clusters"
5 · Check

QA Review

Scores every draft, fixes what it can, and holds back anything that still fails.

"QA these drafts"
6 · Ship

Delivery

Copies approved posts to a dated client folder on the Desktop, as Markdown and Word, with a manifest.

"deliver these posts"
02

Getting the files onto your computerGitHub Desktop

No terminal, no commands to type. GitHub Desktop is a free app that does the same job as git clone with buttons instead — and it's what pulls future updates too, so it's the one setup to learn.

  1. Go to desktop.github.com and download it. Open the installer and click through with the defaults.
  2. Open GitHub Desktop → File → Clone Repository.
  3. Click the URL tab, then paste: https://github.com/cuteniendo/content-seo
  4. Under "Local Path," click Choose… and pick Desktop, then click the blue Clone button.
  5. A folder called content-seo now sits on the Desktop — that's the whole pipeline (skills, scripts, templates, this doc, all of it).
  6. Whenever the pipeline gets updated later: open GitHub Desktop → click Fetch origin, then Pull origin if it offers one. No re-downloading, ever.
Prefer a terminal? Same result, one command.
1# from inside the folder you want it saved in, e.g. Desktop
git clone https://github.com/cuteniendo/content-seo.git

2# to pull a later update, from inside the content-seo folder
git pull
03

Opening it in Claude Code

Claude Code needs to know which folder it's working in before it can see any of the skills. When you start a new local session, it'll ask you to pick a folder — that's the moment this matters.

Select the content-seo folder itself — the one that has skills, scripts, and README.md visible directly inside it once you click into it. Not the Desktop, not a folder above it, not one buried inside it.

Quick way to check you picked correctly: ask Claude "what folders are in here?" If it lists skills, scripts, and templates, the working directory is set right.

04

Starting a run

Once the folder above is open, the whole sequence is wired to one sentence — name the client and how many posts, and it runs all six stations in order.

06

Proposing a change to the pipeline itself

main is protected. A change to a skill or to scripts/ can't land by pushing directly — it goes through a pull request and needs an approving review before it merges. If you ask Claude to push a fix and it bounces, this is why, not a bug:

Awaiting approval → Merging blocked → Reviewed → Merged
Even the repo owner can't approve their own change — GitHub blocks self‑approval outright. So: open the PR, describe what changed and what you tested, and ask the owner to review it. This isn't optional friction; it's the whole point — one accidental edit to a skill file shouldn't be able to change production behavior for every client silently.
